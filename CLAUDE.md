# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project status and map

The project is **feature-complete** (as of Oct 2026): a Flask web app, a Google Sheet sync CLI, and a weekly GitHub Actions automation. Read `README.md` for the user-facing description, troubleshooting table, design decisions and known limitations; this file holds the engineering detail.

- **Default branch is `master`** (not `main`). All code lives there. **`results` is an automation-only branch** created and written by the workflow (CSVs under `recommendations/`, its own history, no shared files with `master`) — never merge `master` into it and don't hand-edit it.
- **Remote:** `github.com/mfannin099/bookRecommendation` (public). Commits in this repo end with the `Co-Authored-By` trailer given by the harness.
- **Two entry points:** `main.py` (web, top 10, stateless) and `scripts/sync_from_sheet.py` (CLI, top 15 by default, what the workflow runs).
- **Layout:** `utils/` = `recommender.py`, `metadata_client.py`, `sheets_client.py`, `book_columns.py`, `book_dates.py`; `scripts/` = `sync_from_sheet.py`, `clean_books_data.py`, `test_metadata_coverage.py`; `tests/test_sheets_client.py` (47 offline tests); `data/recent_20_books.csv` (the only tracked data file; fixture for the cleaner and coverage script); `data/recommendations/` (generated, gitignored).
- **Secrets hygiene (hard rule):** the Google Sheet is link-shared, so its ID is effectively a password. It lives only in the gitignored `.env` locally and the `GOOGLE_SHEET_ID` Actions secret in CI — never in code, docs, tests, commit messages, PR text or logs. Before any push, run `git ls-files -co --exclude-standard | xargs grep -l "<sheet id>"` (must print nothing) and, for history, `git log --all -S"<sheet id>"`. `.gitignore` covers `.env` and `.env.*` (except `.env.example`).
- **Verification habits that worked:** `uv run pytest` (offline); `sync_from_sheet.py --dry-run` to see exactly which books are selected; a live run (`--n 30`, ~5 min) to judge recommendation quality; for workflow changes, parse the YAML (`uv run --with pyyaml python ...`) and simulate the publish script against a throwaway bare repo. Delete generated CSVs under `data/recommendations/` after test runs.

## Commands

This project uses [uv](https://docs.astral.sh/uv/) for dependency management (no virtualenv/pip workflow, no Docker). Dependencies are declared in `pyproject.toml` and pinned in `uv.lock`.

Setup:
```bash
uv sync
```

The web app needs no API key or `.env` file — all three metadata sources (Open Library, Wikipedia, iTunes) are free and keyless. (Only the Google Sheet sync below needs a `.env`, for `GOOGLE_SHEET_ID`.) Coverage on the 20 books in `data/recent_20_books.csv` is 70% (30% Open Library + 15% Wikipedia + 25% iTunes) — see `scripts/test_metadata_coverage.py` to re-measure after further data or code changes.

Run the Flask app (dev):
```bash
uv run python main.py        # serves on 0.0.0.0:5001
```

Run the recommender standalone, outside the web UI (against the hardcoded `BOOKS` list at the top of the file):
```bash
uv run python quick_start.py
```

Add a new dependency:
```bash
uv add <package>
```

Re-clean `data/recent_20_books.csv` in place (idempotent):
```bash
uv run python scripts/clean_books_data.py
```

Measure `MetadataClient` description coverage (Open Library vs. Wikipedia fallback vs. iTunes vs. not found) against the books in `data/recent_20_books.csv` (looked up by first author, as the sync does):
```bash
uv run python scripts/test_metadata_coverage.py
```

Sync the most recent books from the personal Google Sheet and write recommendations to `data/recommendations/matt_book_recommendations_<date>_<genres>.csv` (gitignored). Needs `GOOGLE_SHEET_ID` in a gitignored `.env` (copy `.env.example`) or the environment — the sheet ID is the only thing protecting a link-shared sheet, so it must never be committed, hardcoded, or printed. `--n` is the look-back count (default 20, max 50); `--top` is how many recommendations to return (default 15, max 50); `--genres` defaults to `analytics,strategy,business,data` (`--genres ""` for none); `--dry-run` lists the books and stops, with no metadata lookups:
```bash
uv run python scripts/sync_from_sheet.py --dry-run
uv run python scripts/sync_from_sheet.py --n 30 --genres "golf,business"
```

The scheduled run lives in `.github/workflows/weekly-recommendations.yml` (Saturdays 12:17 UTC; also `workflow_dispatch`): it runs the tests, then `sync_from_sheet.py` with default genres and again with `habits,discipline,mindset`, and commits the CSVs to an auto-created `results` branch (`recommendations/`) via a side `git worktree`. It needs the `GOOGLE_SHEET_ID` repository secret. The repo is public, so Actions logs and `results` expose book titles and recommendations (not the sheet ID). `sync_from_sheet.py` returns exit code 1 with a one-line `Error:` for sheet and recommender failures so a failed CI step is readable.

Run the tests (pytest, dev dependency; no network — they cover the sheet row-selection rules, date parsing and output filenames):
```bash
uv run pytest
```

There is no lint, typecheck, or build step configured in this repo.

## Architecture

Three-part app: a stateless-ish Flask frontend (`main.py`), a metadata lookup client (`utils/metadata_client.py`), and a recommendation engine (`utils/recommender.py`) built on top of it. Around that core sit a CLI sync from a Google Sheet (`scripts/sync_from_sheet.py`, `utils/sheets_client.py`) and a weekly GitHub Actions workflow that runs it — described in the "Google Sheet sync" and "Weekly automation" paragraphs below.

**State handling (`main.py`):** The book/author list the user builds up isn't stored in a database or on disk at all — it's held purely in the module-level `book_list`/`author_list` globals (position-paired: index N of one corresponds to index N of the other), so this app is designed for a single ephemeral session, not multi-user persistence, and nothing survives a restart. Routes: `/` (add/list entries), `/upload` (bulk-add from one or more uploaded `.csv`/`.xlsx`/`.txt` files — parsed by `parse_book_file`), `/edit`, `/delete`, `/clear`, and `/recommend` (triggers the recommendation pipeline and renders `recommend.html`). `/recommend` passes `list(zip(book_list, author_list))` straight into `BookRecommender(books=...)` — no file round-trip. It also reads an optional `genres` query param (comma-separated, e.g. `?genres=golf,business`) from the homepage's "Get Recommendations" form and passes it through as `genre_keywords` — typed fresh per request, nothing persisted.

Since `/recommend` can take minutes (see "Why it's slow" in README.md), it also passes `on_progress=recommend_progress.update` to `BookRecommender` — a module-level global dict (`recommend_progress`, cleared at the start of each `/recommend` call) that the pipeline writes into as it works. A separate `/recommend/progress` route just returns that dict as JSON, polled every second by `index.html`'s loading-overlay JS (`fetch('/recommend/progress')` on a `setInterval`, started when the recommend form is submitted) to show live status — which book/candidate, out of how many, and which source found it. This only works because `app.run(..., threaded=True)`: the dev server needs to serve the polling request concurrently with the still-running `/recommend` request, not queue it behind it. Like `book_list`, `recommend_progress` is a single global, not per-session — fine for this app's documented single-user/ephemeral scope, but would clobber across concurrent users.

Both the manual-add form and `/upload` dedupe against the existing list via `_dedupe_key(title, author)` (imported in `main.py` from `utils/book_columns.py`'s `dedupe_key`) (case-insensitive exact match on the pair) before appending — duplicates are skipped rather than silently added, since a duplicate read-book double-weights that book's vocabulary in the TF-IDF profile, not just clutters the list. `/upload` reports counts back via `redirect(f'/?added={added}&skipped={skipped}')`, which `index.html` reads from `request.args` to show a one-line summary (no session/flash machinery needed) — rendered as a colored `.success-message`/`.warning-message` banner (`static/style.css`) right below the page header, above the forms, so it's visible without scrolling. All error paths (`/upload`'s bad-file-type/missing-columns/parse failures, `/recommend`'s "no books yet") render `error.html` for a consistent, auto-redirecting error page instead of raw inline HTML strings.

`parse_book_file`'s `.txt` format splits each `Title - Author` line on the *last* `" - "` (`rsplit`), not the first — a subtitled title containing its own `" - "` (e.g. "Chip War - The Fight for the World's Most Critical Technology") would otherwise get split in the wrong place, since an author name essentially never contains `" - "` but a nonfiction subtitle commonly does.

`.csv`/`.xlsx`/`.xls` column matching (`_find_column`, i.e. `utils/book_columns.find_column`, shared with the sheet sync) accepts aliases, not just the literal words "title"/"author" — `TITLE_COLUMN_ALIASES = {"title", "book", "book title", "name"}`, `AUTHOR_COLUMN_ALIASES = {"author", "authors", "author name", "writer"}` — since real export tools vary (StoryGraph uses "Authors" plural, LibraryThing often uses "Primary Author"). `_read_tabular` also tries a `.csv` as comma-, then semicolon-, then tab-delimited in turn, accepting the first that actually yields a recognizable title *and* author column, since non-US Excel locales default to semicolon-separated exports — this can't misinterpret a correctly comma-delimited file that merely has a stray semicolon in some data field, since a wrong separator essentially never happens to produce column headers that match an alias. When no column is found under any alias/separator, the error message lists the columns actually present, rather than just asserting "must have title and author columns" with no way to self-diagnose why.

**Metadata lookup (`utils/metadata_client.py`):** `MetadataClient.fetch(title, author)` tries three sources in order, stopping at the first usable description: Open Library (`fetch_from_open_library` — search by title/author, then fetch the work's `description`/`subjects`), Wikipedia (`fetch_from_wikipedia`), then Apple's iTunes Search API / ebook listings (`fetch_from_itunes`). Both fallbacks do a loose free-text search that can return a wrong-but-plausible page/listing rather than no result, so both validate before trusting a match: Wikipedia requires the author's name to appear in the returned page's lead-section extract; iTunes requires *both* the author's name to appear in the listing's `artistName` *and* the title to fuzzy-match (`thefuzz`, `ITUNES_TITLE_MATCH_THRESHOLD = 70`) the listing's `trackName` — author-only matching isn't enough for iTunes since it can surface a different book by the same author (a companion/summary title, another edition) that an author check alone wouldn't catch. iTunes descriptions are HTML-formatted marketing copy, cleaned via `_strip_html` (strip tags, unescape entities, collapse whitespace) before use. `_wikipedia_get` retries with backoff on Wikipedia's 429 rate limit; iTunes has no documented rate limit or a clean signal to react to if one is hit, so `itunes_pause` (default 1.0s) is a flat, conservative guess rather than adaptive backoff. No API key needed for any of the three sources. `MetadataClient.fetch` sleeps `open_library_pause` (default 0.2s, a light courtesy delay — Open Library has no documented rate limit) before the Open Library attempt, and `wikipedia_pause` (default 0.5s) before falling back to Wikipedia. All request call sites (`fetch_from_open_library` x2, `_wikipedia_get`, `fetch_from_itunes`, `search_open_library_candidates`) go through one module-level `_SESSION = requests.Session()` rather than bare `requests.get(...)`, so repeated requests reuse an already-open connection per host instead of a fresh TCP+TLS handshake each time — safe to share across the thread pool below since `requests`' underlying connection pool is internally lock-protected. `DEFAULT_HEADERS` (the descriptive User-Agent Wikipedia requires) is set on `_SESSION` once at module load rather than passed per-call. Even so, a full pipeline run is many requests over a real network — see "Why it's slow" in README.md. Also exposes `search_open_library_candidates(query)` for discovering new, not-yet-read books.

**Recommendation pipeline (`utils/recommender.py`, `BookRecommender` class):** `BookRecommender(books=[(title, author), ...], ...)` takes the read-books list directly (no file paths — `titles_list`/`authors_list` are derived from `books` in `__init__`). An optional `on_progress` callback (default `None`, fully additive — nothing changes if omitted) gets called via `self._report(phase, **details)` at each meaningful step: once per book/candidate finishing its metadata lookup (`phase="reading_library"`/`"checking_candidates"`, with `completed`/`total`/`title`/`source`), and once at each phase boundary (`"searching_open_library"` with the query, `"ranking"`). `main.py` is the only current consumer, wiring it to a module-level dict polled by the homepage's loading screen — see "State handling" above. `get_recommendations()` then runs these steps in order:
1. `load_or_build_library` — call `MetadataClient.fetch` for each (title, author) pair, or load a cached copy from `library.parquet` (skipped when `force_run=True`, which `main.py` always sets). The fetches run on a bounded `ThreadPoolExecutor` (`max_workers`, default 5, constructor param) rather than one at a time — each fetch is I/O-bound, so this cuts wall-clock time roughly `max_workers`-fold without materially increasing CPU/memory use. Lower `max_workers` on a more constrained machine; raise it for more speed at the cost of more concurrent load on Open Library/Wikipedia.
2. `clean_library` — drop books with no usable description, strip punctuation for TF-IDF. If `genre_keywords` is set (e.g. `["golf"]`, passed through from `/recommend`'s optional `genres` query param), each keyword is appended to every row's `clean_description`, repeated `genre_boost_repeats` times (default 5, a deliberately light touch) — this is the single injection point for genre-steering, shifting both the TF-IDF vocabulary used in the next step and the profile centroid used for ranking (`rank_candidates`) toward the genre, without the user's actual books losing most of the signal.
3. `build_search_query` — TF-IDF (`scikit-learn`) over the cleaned descriptions to extract the top terms (default 3, reduced by `len(genre_keywords)` to keep the same overall budget) as an Open Library search query, then `genre_keywords` are unioned in (deduped, so a keyword that also rose naturally via the boost above isn't repeated) — guaranteed included rather than relying on the boost alone to make them statistically dominant. Kept small deliberately: Open Library's `q=` search is a strict AND across terms, so more than a handful collapses the result count to near zero. The `TfidfVectorizer` built in `get_recommendations` uses `STOP_WORDS` (sklearn's standard English list plus `BOOK_BOILERPLATE_STOPWORDS` — "new", "book", "times", "author", "york", etc.), not bare `stop_words="english"`: book-marketing/citation boilerplate (especially pervasive in the iTunes fallback's promotional-copy descriptions, e.g. "...New York Times bestselling author...") isn't in sklearn's standard stopword list but appears in enough descriptions to dominate the TF-IDF sum this method ranks by, producing a near-meaningless query like `"book new times"` instead of anything topical. Measured live on real data: fixed a 20-book profile's query from `'book new times'` (which surfaced a romance novel, a cookbook matched purely on "New York Times", and two fantasy novels as "recommendations") to `'business supply chain'` (every result on-topic). `BOOK_BOILERPLATE_STOPWORDS` also includes a second group of generic marketing superlatives ("visionary", "groundbreaking", "compelling", "masterful", etc.) — found live on a 10-book business profile, where "visionary" (a legitimate top term, from Steve Jobs/Elon Musk bios) also matched a William Gibson sci-fi novel whose own blurb separately calls Gibson "one of the most visionary... writers". Removing a contaminating term from this list can let a different, equally generic term take its place in the top-3 selection rather than a topical one — confirmed when removing "visionary" let "sector" fill the freed slot, which pulled in a cluster of unrelated healthcare books that scored *higher* than the sci-fi novel had; "sector"/"sectors" was added to the list to fix that specific case. This whack-a-mole dynamic means the stopword list is a reactive, not a permanent, fix — each addition has only been verified against the profiles tested so far, not proven to generalize. See `rank_candidates`' category-overlap boost below for a complementary (not equivalent) signal.
4. `fetch_candidates` — search Open Library with that query, excluding anything fuzzy-matching (`thefuzz`, `already_read_match_score`, default 85) an already-read title, *and* excluding anything fuzzy-matching a candidate already kept this run — Open Library often returns the same work twice as separate editions differing only in case/whitespace (e.g. "The Man Who Loved China" / "the man who loved china"), which would otherwise occupy two of the final slots. `top_subjects` separately counts usable subject/category tags (`_is_usable_subject`, filters Open Library's crowdsourced noise — call numbers, foreign-language duplicates, marketing tags like "New York Times bestseller"; also drops `_GENERIC_SUBJECTS` such as "Books", "Nonfiction", "History", "Biography", because "most popular books tagged X" for those returns the same crowd-pleasers — *Shoe Dog*, *Born a Crime*, *Into Thin Air* — for every profile) across every matched book's already-fetched `categories` column (previously collected by every metadata source and never used anywhere), returning the `subject_count` (default 3) most common. `fetch_subject_candidates` then searches Open Library's `/subjects/{slug}.json?sort=rating` endpoint per subject — a *popularity*-ranked signal the keyword search has no equivalent of (confirmed directly: the keyword search's `search.json` has no way to prefer *How to Win Friends and Influence People* over an obscure, barely-cataloged work on the same topic; the subjects endpoint's `sort=rating`/`sort=want_to_read` does). `_merge_candidates` combines both candidate sources, deduping anything fuzzy-matching a candidate already kept (the same work can surface from both). Measured on a 5-book business-focused test profile: 8 of the final 10 recommendations (including *Steve Jobs*, *Elon Musk*, *Start with Why*) came *only* from the subject-based source, not the keyword search — this also doubles as a partial answer to the single-theme-convergence limitation noted below, since multiple distinct subjects can be queried where one TF-IDF query converges on whichever term wins.
5. `enrich_candidates` — fetch descriptions (and subtitle, when present) for the surviving candidates via `MetadataClient`, same bounded thread pool as step 1. With `candidate_pool_size=40` by default, this step is the dominant cost in the whole pipeline.
6. `rank_candidates` — cosine similarity (`sklearn.metrics.pairwise.cosine_similarity`) between each candidate and the centroid of the read-books' TF-IDF vectors; candidates below `min_similarity` (default 0.05) are dropped rather than padding the result out to `top_n` regardless of match quality (a bare top-3-TF-IDF-term Open Library search can surface a spurious keyword-collision match — e.g. Ray Bradbury's *Death Is a Lonely Business* matching on the word "business" alone — that a similarity floor filters back out); returns up to `top_n` (default 10) as a DataFrame with `title`, `subtitle`, `authors`, a `description` snippet (truncated to ~240 chars at a word boundary), and the raw `similarity` score. Before that filter, each candidate's raw similarity gets a modest multiplicative boost — `* (1 + 0.15 * overlap)` — for every one of its own `categories` (carried through from `enrich_candidates`, previously discarded) that case-insensitively matches the profile's `top_subjects` (`_subject_overlap`), a light nudge in the same spirit as `genre_boost_repeats` rather than a hard override of the text-similarity signal. This targets the same class of problem as the stopword list above but from the other direction — surface-vocabulary false positives that share generic wording with the profile despite being topically unrelated — and only helps when the candidate actually has category data to compare: confirmed live that a pharma book with zero Open Library subjects scored above several legitimate picks purely on shared business-strategy vocabulary ("stakeholders", "new era"), a case this boost can't touch and that stays a known, open limitation of TF-IDF's surface-vocabulary matching.

`get_recommendations()` also sets `self.total_book_count` (`len(titles_list)`) and `self.matched_book_count` (`len(profile_df)`, i.e. how many of those actually had a usable description) before raising on an empty profile, so `main.py` can read them straight off the `BookRecommender` instance after the call and `recommend.html` shows "Based on N of M books" (plus a "couldn't be matched" note when `N < M`) without the pipeline needing to return anything beyond the recommendations DataFrame.

`MetadataClient` itself needed no changes to support this — `fetch()` only reads its own immutable `open_library_pause`/`wikipedia_pause` attributes and has no shared mutable state, so it's already safe to call concurrently from multiple threads.

Every call to `/recommend` rebuilds the library from the API rather than trusting the parquet cache (`force_run=True`), so the cache in `main.py`'s flow is effectively unused — it only matters when running `BookRecommender` directly (e.g. from `quick_start.py`) with `force_run=False`. `library.parquet` is gitignored (it's a rebuildable cache, not project data).

Templates (`templates/*.html`) are plain Jinja2 with no shared base template; `static/style.css` is the only styling. `notebooks/nltk_playground.ipynb` is a scratch notebook for NLP experimentation and isn't part of the app's runtime path.

**Google Sheet sync (`scripts/sync_from_sheet.py`, `utils/sheets_client.py`):** CLI-only (no Flask route) path from the personal tracker sheet to recommendations. The sheet is shared as "anyone with the link: Viewer", so `fetch_sheet()` reads it as CSV from the export URL with no Google auth; `GOOGLE_SHEET_ID` (optional `GOOGLE_SHEET_GID`, default first tab) comes from `.env` via `python-dotenv`, and every error path avoids echoing the URL (`requests` exceptions embed it, so only the exception type is reported). `recent_tracked_books(df, n)` is the pure row-selection function: a row is "tracked" if it has a `year` or a parseable start/end date (so audiobooks logged with a year but no dates count, while the ~190 older undated "want to read" rows don't); rows missing a title or author are dropped; duplicates (case/whitespace-insensitive via `dedupe_key`) keep their last occurrence; and the result is the last `n` rows in **sheet order** (the sheet is appended chronologically), not re-sorted by date. `validate_n` is the single definition of the 1..`MAX_BOOKS` (50) limit, used by both the CLI's argparse type and the function. Dates go through `utils/book_dates.parse_date` (moved out of `scripts/clean_books_data.py`, which now imports it). The script passes `--genres` through as `genre_keywords` and names its output `matt_book_recommendations_<date>_<genres>.csv`. Known gap: author strings are passed to the lookups as written (e.g. `A & B`), unlike `clean_books_data.py` which normalizes `&`/`and` to commas. Tests live in `tests/test_sheets_client.py`.

**Data cleaning (`scripts/clean_books_data.py`):** Standalone script (unrelated to the Flask app's `/recommend` pipeline) that re-cleans `data/recent_20_books.csv` in place. It is idempotent: an already-cleaned file carries the original date text in `start_date_raw`/`end_date_raw`, which the script re-parses, so running it again changes nothing. It keeps the most complete row per (title, author) when a book appears twice (a bare "want to read" row plus a filled-in one), normalizes `&`/`and` in authors to `, ` (handling an existing Oxford comma), lowercases/sorts genre tags, and parses messy dates via `utils/book_dates.parse_date` (day-month dates resolve against the `year` column; fuzzy references like "early jan" approximate to day 5/15/25; unparseable ones stay `NaT` with the original text preserved). `data/recent_20_books.csv` is also the fixture for `scripts/test_metadata_coverage.py`.

**Weekly automation (`.github/workflows/weekly-recommendations.yml`):** triggers are `schedule` (`17 12 * * 6` = Saturday 12:17 UTC = 8:17 AM EDT / 7:17 AM EST; deliberately off the top of the hour) and `workflow_dispatch` (input `n`, default 30; scheduled runs fall back to 30 via `inputs.n || '30'`, passed through `env`, never interpolated into the shell). Permissions `contents: write`; `concurrency` group `weekly-recommendations` (no cancel); `timeout-minutes: 60`. Steps: checkout `master` → `astral-sh/setup-uv` → `uv sync --frozen` → `uv run pytest -q` → secret-present check → sync with default genres → sync with `habits,discipline,mindset` (`if: ${{ !cancelled() }}` so it still runs after a failure) → publish. Publish uses a side `git worktree` (`results-wt`): if `origin/results` exists it is checked out (`-B results origin/results`), otherwise an orphan branch is created; the day's CSVs are copied to `recommendations/`, committed as `github-actions[bot]` (`Weekly recommendations <UTC date>`) and pushed, with no commit when nothing changed. One job running the two lists sequentially (not a matrix) avoids two jobs racing to push `results` and halves concurrent load on Open Library. Files are named by UTC date and genre slug, so two runs on the same day with the same genres overwrite each other's file.

**Scheduler reality (observed, not assumed):** GitHub cron is best-effort. The first slot (12:00 UTC, Oct 10 2026) never fired; after adding a one-off `14 15 10 10 *` test cron (since removed), the run that appeared started at 19:17 UTC (~4 h late), succeeded in ~10 min, and published to `results`. GitHub exposes no "upcoming runs" view and logs nothing for skipped slots; the only evidence of a scheduled run is a run with event `schedule` (`curl https://api.github.com/repos/mfannin099/bookRecommendation/actions/runs` works unauthenticated on this public repo). Scheduled workflows only run from the default branch's latest commit, are not triggered by pushes (no `push` trigger), and may be disabled after ~60 days without repo activity. Cron ignores DST: shift to `17 13` after Nov 1 to keep 8:17 AM Eastern. Pushing a workflow edit to `master` does not start a run; use the Actions tab's **Run workflow** to test.

**Genre keywords and recommendation quality (what was learned):** `--genres` keywords are both appended to the TF-IDF profile text and ANDed into the Open Library keyword search, so *more keywords = fewer candidates*, and a thin candidate pool is padded with generic popular books (the "filler tail": *Shoe Dog*, *Born a Crime*, *Into Thin Air*, *Midnight in Chernobyl*). Two mitigations are in place: `BOOK_BOILERPLATE_STOPWORDS` and `_GENERIC_SUBJECTS` (generic subject tags are excluded from `top_subjects`, so subject-based discovery doesn't return the same crowd-pleasers for every profile). The effect of `_GENERIC_SUBJECTS` was *not* measured before shipping (the confirming run was skipped), so treat it as unverified. Live results on a 30-book profile: `analytics,strategy,business,data` ≈ 13/15 on topic (default); `data,business` fine with a weaker tail; `machine learning,...` all academic textbooks; `habits,discipline,mindset` ≈ 4/15 on topic before the subject filter; `motivation,productivity` and `psychology,self-help` ≈ 2/10. Concrete topic nouns beat umbrella labels like "self-help".

**Author handling:** `utils/book_columns.first_author` splits on `,` `;` `&` and the word "and" (word boundaries, so "Alexander" is safe) and returns the first name. `sync_from_sheet.py` applies it only when building the `BookRecommender` input — the CSV/dry-run still show the full string. Rationale (verified live): Open Library's `author=` filter is loose (any listed author works), but Wikipedia/iTunes require the *entire* author string to appear in the page extract / `artistName`, so `"A & B"` fails where `"A"` matches. The Flask upload/manual-add paths do **not** apply it. `clean_books_data.py` instead normalizes `&`/`and` to `, `.

**Known limitations / possible follow-ups:** metadata coverage ≈ 70% (some correctly-spelled books are in none of the three sources); TF-IDF ranking is surface-vocabulary overlap (embedding-based ranking was scoped but not built — evaluate by hiding the 5 newest books and checking their rank); near-duplicate editions with long subtitles can both appear; the web app is still top 10 / full author strings; `pyarrow` in `pyproject.toml` is unused since the parquet output was removed; Open Library intermittently times out or 500s (a single lookup is dropped, so results vary slightly run to run); public repo means logs/`results` expose titles and recommendations; sheet placeholder authors (e.g. "Many Authors") can't match. Other unbuilt ideas: extra metadata source with an API key secret, recency-weighted profile, email notification, lookup cache, a backup cron (would double-publish when both fire).
